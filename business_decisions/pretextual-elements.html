The framing

The core insight

The question isn't "can we detect pré-textuais?" — it's which pré-textual, because they are not the same kind of thing.

Some pré-textuais announce themselves with a fixed heading word — RESUMO, ABSTRACT, SUMÁRIO, LISTA DE TABELAS. Those are an exact match for the deterministic, anchored-regex approach the pipeline already uses for the post-textual Apêndice and Anexo sections in postTextual.ts. No AI, no template, no guessing.

The cover pages — capa, folha de rosto, folha de aprovação — are different. They carry no heading word, just a free layout of institution, author, title, advisor, city, and year. We can detect where they are with high confidence, but we cannot always tell which line is which field with no formatting cue. And we cannot borrow that data from elsewhere: the uploader is not guaranteed to be the author, and the project title may be a placeholder like "thesis". So the data must come from the document or from the user — which is exactly why these need a confirm step.

The why

Reasoning, bucket by bucket

Bucket 1 — labeled sections are a solved pattern

Deterministic

Resumo, Abstract, Sumário, the listas, Agradecimentos and Errata all open with a fixed, unnumbered heading word. A new preTextual.ts mirroring postTextual.ts can anchor each label at both ends (^…$), so an in-body mention never matches, then apply the unnumberedTitle style. That style is already specified in the ABNT spec (§8) and flagged as not-yet-applied — this wires it up. Cheapest, most reliable win; ship first.

Bucket 2 — cover pages: region is detectable, fields are not

Detect + confirm

We can locate the cover region deterministically: page position, the lone year line as a hard bottom anchor, the natureza note ("apresentado ao… como requisito parcial…") and the orientador line as folha-de-rosto fingerprints. What stays ambiguous is telling author from title from institution when all three are plain centered lines. So the pipeline parses its best guess, then shows the user a pre-filled form to confirm or correct before the cover is rebuilt to ABNT spacing. No silent guessing on someone's thesis cover.

The data-source rule that forces the confirm step

Detect + confirm

We deliberately do not fall back to account name as the author or the project title as the document title. The uploader may not be the author, and the project title can be a stand-in like "thesis". That removes the one shortcut that could have skipped the form — which is precisely why detect-and-confirm, not parse-only, is the right call here.

Bucket 3 — the Sumário's contents should be regenerated

Regenerate

Step D already produces a corrected heading tree (title / h1 / h2 / h3). The Sumário entries should be built from that tree, not reformatted from whatever the author typed — a reformat would faithfully reproduce their mistakes. The open issue is page numbers: DOCX has no page metadata (the same wall the references locator hits), so numbering needs either a Word TOC field that updates on open, or a render pass. Worth deciding on its own.

The call

Recommendation

Build in three independent slices, in this order.

1 · Labeled sections. Add preTextual.ts (anchored-regex detection mirroring postTextual.ts) and wire the unnumberedTitle style into Step A. Fully deterministic, no UI change, no AI — lands fast and stands alone.

2 · Cover pages, detect-and-confirm. Deterministic region detection (year anchor + natureza/orientador regex) extracts a best-guess field set; a new confirm screen lets the user correct it; deterministic generation rebuilds capa / folha de rosto / folha de aprovação from those confirmed fields.

3 · Sumário regeneration. Build entries from the Step D heading tree, after the page-numbering question is settled.

Honest caveat: slice 2 adds a step to the user flow and a parser whose accuracy will need real-document tuning. But the confirm screen is the safety net — a weak parse costs the user a few corrections, never a wrong author silently printed on their cover.

Still to settle

Open questions

Sumário page numbers

Word TOC field that updates on open (zero numbering logic, but requires a real Word style/field), or a render pass to compute numbers ourselves? DOCX gives us no page metadata either way.

Where the confirm screen lives in the flow

A new step between processing and download, or folded into the existing needs_input mechanism already used for missing captions/sources (pending_inputs)? The latter reuses machinery that exists.

Missing covers

When a document has no capa or no folha de rosto at all — do we offer to generate one from scratch via the same confirm form, or leave it untouched? This decides whether the form is "correct what we found" or "fill in what's needed".
